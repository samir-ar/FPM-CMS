### Security

- **`GET /api/v2/member-photo/{memberId}` now only serves the photo of a representative (`persons.member_id`) or an election candidate (`internal_election_candidates.member_id`)**; any other member id returns 404 (it used to return any member's real photo, with no login). Side effect, accepted earlier: the admin "search members to add as a candidate" preview is blank for members who are not yet candidates.
- **`userPolls` and `volunteerUsers` admin resources now follow the Polls / Volunteers page permission** (they had no permission check at all - any logged-in admin could open them). Resolved by page `url`, view for list/show, full for the rest.
- **Shared upload/delete helpers (`upload-image`, `delete-image`) now require Full control of at least one page** (new `any-full` middleware); a View-only admin or one with no Profile can no longer upload or delete files.
- Session tokens (`generate_token`) and the 4-digit SMS codes (`generatePIN`) now come from `random_bytes` / `random_int` instead of `mt_rand`.

### Fixed

- **Titles (and any other text field) with an apostrophe were cut when edited in the CMS.** The shared form helper (`FormTrait::drawHtml`) pasted the saved value raw inside `value='...'` for every text / number / hidden input, so a title like `Monaco's money...` or `... ال'محامين'` ended the attribute at the apostrophe: the edit form showed it cut there, and saving the form wrote the CUT text back to the database - which is how a news title ended mid-word ("...في نقابة ال"). Values and placeholders are now HTML-escaped (affects every CMS form). **Titles already saved cut stay cut and have to be retyped** (the missing end is not stored anywhere); titles never re-saved are still complete.
- **Likes and shares on EVENTS in the Home feed were lost on refresh (and could land on a news article).** Only news could be liked: the feed reported `like: null` for events, and the app sent an event's id to `news-like` / `news-share`, so the like was either rejected or attached to whichever news article had the same numeric id, and never came back. Events now have their own `event_likes` table (unique per user+event) and an `events.shares` counter, new endpoints `POST event-like` / `POST event-share`, and the Home feed (`get-wall-feed`) reports `likes_nb` / `like` for events. **Needs the new app release** - app builds before 4.4.22 still send event likes to the news endpoints. Any news likes that were wrongly attached to a news article by an old build cannot be told apart from real ones.
- **`fpm_users.PersonImage` widened to MEDIUMBLOB** (it was a TEXT/BLOB capped at 65,535 bytes, which silently cut every larger member photo mid-file; 658 of 40,500 staging rows are exactly 65,535 bytes). Migration is idempotent, relaxes `sql_mode` for its own session only (some rows hold an invalid `0000-00-00` date_of_birth that strict mode refuses mid-ALTER), and keeps every byte. Photos already truncated stay truncated until the TWH sync sends them again.

### Security (continued)

- **National Council poll voting hardened** (previously: no unique key, "already voted" check not atomic, poll_id trusted from the request): votes are tied to the MEMBER (`member_id`) with a unique `(poll_id, question_id, member_id)` key, so a second app account or a parallel request cannot vote twice; the poll voted on is chosen by the server, every answer must belong to a question of that poll, a question can be answered once, and all rows are written in one transaction. `device_id` and `voted_at` are stored. The migration refuses to run over existing double votes.
- National Council endpoints now sit behind the app-signature middleware and a separate `national_council_min_build` setting (CMS Settings page, blank = no restriction; set it only after the new app is live in both stores).
- "Delete all data" is refused on a published poll and a poll that already has votes cannot be deleted.

### Security and vote integrity (2026-11-18/19)

- **Login and SMS code hardening.** (1) `send-verification` no longer returns the code in its reply (anyone knowing a member id + phone number could read it and log in without the phone). (2) The server used to mark the account verified the moment the code was SENT, so the token in that reply already worked without the code: the new token now waits in `app_users.pending_token` and replaces the real `token` only when the right code is entered (`RegistrationRepository::completeVerification`); asking for a code no longer logs the real member out. (3) A code lives 10 minutes and works once; 10 wrong tries per member / 40 per IP in 15 minutes lock the login; at most 5 code requests per member in 15 minutes. (4) The unversioned `/api/send-verification` and `/api/verify-pin` now use the same controller. (5) An empty pin can no longer delete an account. Migration `2026_11_18_160000` (`pending_token`, `verification_expires_at`). The delete-account code still has no wrong-try limit.
- **The fixed code `1111` now exists only for Apple's review number (96176979532)** (`RegistrationRepository::APPLE_REVIEW_PHONE`). It was also accepted for 96171106394, 96178837076, +9613956719 (a real voter) and +9613706108.
- **The SMS provider login is no longer in the code:** `.env` keys `SMS_URL`, `SMS_USERNAME`, `SMS_PASSWORD`, `SMS_FROM` (read through `config('services.sms')`); a missing key stops with a clear error instead of silently not sending. The old values are still in git history: change the provider password.
- **One vote per MEMBER, enforced by the database.** A vote is saved against an app account and one member could hold several accounts. Internal election: a member who voted through any account carrying their member id (leading zero ignored) cannot vote again (checked in `canIVote` and again just before saving). Regular polls: one answer per member (answers can no longer be changed; the app says "You already voted", error code `already_voted`). Council polls already had it. Migration `2026_11_18_170000` adds `member_key` (member id without leading zeros) to `internal_election_votes` and `users_polls` with unique rules per election / per poll; old duplicate rows are kept with a NULL key. Guests on regular polls count once per PHONE (`hardware_id`; the app's own `device_id` changes on reinstall); a guest vote without a hardware id is refused, so old builds must update. The legacy root `answer-poll` route now uses the same checks.
- **One active app account per member, enforced by the database.** Migration `2026_11_19_100000` adds the computed column `app_users.active_member_key` with a unique index: two active accounts of one member (leading zero ignored) can no longer exist; soft-deleted accounts and accounts without a member id are not counted. The migration refuses to run while duplicates exist. The login lookup (`UserRepository::getUserByPhoneNumber`) now treats the MEMBER ID as the identity: it reuses the member's own account whatever phone it was created with and never returns another member's account (it used to match "member id OR phone, newest first", so on a shared phone - about 1,000 members share a phone number - one member's login could overwrite another's account row). The admin Excel import skips a member who already has an account; a login race reuses the account that won. `app-users:dedupe` now keeps the account that holds internal-election / council votes, otherwise the one really used most recently (`user_activity_logs`), and merges leading-zero twins. Production clean-up of 2026-11-19: 14,396 members / 17,381 accounts hidden, no vote left on a hidden account. The vote -> voter relations include hidden accounts.
- **بلديات, مخاتير and التنظيم الداخلي endpoints** now need a valid member login AND the signed request (they used to need only the signature, التنظيم الداخلي nothing). Per member: at most 50 pulls per hour and 150 per day (a pull = one screen opened), every pull is logged (`directory_pull`), a warning is logged at 100 pulls in a day (`directory_pull_heavy_use`) and when a cap is hit. ### Added
